# Speech and processing settings

`ProcessingScreen` accepts the shared `FeatureScreenProps` and an optional `onTransmitSpeech(jobId,radioId,signal)` callback from the radio/media shell for explicit prepared speech transmission. It must be rendered inside `StationProvider` (radio names and automation cards come from `useStation()`).

Sections (a segmented control; visited sections stay mounted so drafts survive switching):

- **Speech & jobs** (`components/RunSection.tsx`): `SpeechFlow` is a visible Edit → Generate → Preview → Transmit stepper. Transmit is enabled only for a completed audio preview of the current text that was played in the browser (or, on native, explicitly acknowledged), with a radio selected; it asks for confirmation, can be stopped, and is aborted when the screen is hidden, the radio or session changes, or the component unmounts. Editing the text invalidates the preview. `JobRunner` runs transcription/analysis profiles on a radio-history communication. `JobsList` shows status icons, lifecycle progress, results, previews and cancellation, and polls only while jobs are in flight.
- **Providers** (`ConnectionsSection`, `ConnectionWizard`): connector cards (capability chips, Local/Cloud and Simulated badges) → credentials (display name, endpoint, capabilities, API key stored encrypted) → options (`SchemaForm` from an exposed schema, else a curated schema per known connector ID, else Advanced JSON) → review and save. Saving does not contact the provider. The OpenAI subscription flow is shown as an informational card.
- **Profiles** (`ProfilesSection`, `ProfileEditor`): task cards, model picker (known models plus free text), settings via `SchemaForm` with Advanced JSON fallback, and an explained "Allow cloud processing" toggle.
- **Automatic RX** (administrators): one card per radio with the existing consent text, a service-owner user picker (the same `GET admin/users` response the permission matrix uses, validated with `PublicUserSchema`; it falls back to a user ID field when the list is unavailable or invalid) and confirmation dialogs for enabling and disabling.

Pure logic lives in `processing-model.ts` (tested in `processing-model.test.ts`); routes are in `processing-api.ts`; `useProcessing.ts` owns loading, the single-action runner and job polling. Secrets stay on the backend and the API-key input clears after every save attempt. Session or radio changes abort pending requests and clear private results and previews. Browser previews use authenticated blobs, never bearer tokens in URLs, and object URLs are revoked on replacement and unmount. Native playback and actual device acceptance remain gates. See the [implementation guide](../../../../../docs/implementation/processing.md).
