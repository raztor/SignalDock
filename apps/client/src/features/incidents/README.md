# Incidents and alerts

`IncidentsScreen` accepts shared `FeatureScreenProps` and renders permitted-radio incidents as a board (`IncidentBoard`): New → Acknowledged → In progress → Closed (resolved + dismissed), each column paginated by state. Wide layouts show four columns; compact layouts pick one with a segmented control. Cards show priority as shape and text (▲▲ Critical, ▲ High, ● Medium, ○ Low), title, radio, frequency of the first evidence clip (marked "(inferred)" or "(unknown source)" when not confirmed, also in the card's accessible label), age, owner initials and evidence count. It must render inside `StationProvider` (radio names, tuning ranges) and `ToastProvider`. The optional `focusIncident: { incidentId, requestId }` prop (used by the command palette) opens that incident's detail; a new `requestId` reopens it.

Moves are explicit buttons that follow the API's transition table and send the `expectedRevision` of the record the operator acted on (the one rendered), never a newer revision fetched in the background. A failed move reloads the incident; on a revision conflict the close sheet closes and the detail explains that someone else changed the incident, so the operator decides again against its current state. Opening a card shows its column on the compact board (also used beside a side detail), moves focus to the detail heading, and closing the detail returns focus to the card. Resolve and Dismiss open `CloseIncidentSheet`: a reason chip (Handled on air, False alarm, Escalated, Duplicate, Other) and an optional note become the decision note `"<reason>: <note>"`, so the API's required-note rule is always met ("Other" needs a note). `IncidentDetail` plays each evidence clip with the History `RecordingPlayer`, quotes the transcript, and offers assign-to-me, evidence hold (releasing asks first), operator notes, history and assessment provenance.

Administrators manage literal detection rules in `RuleBuilder`: phrases are chips (serialized to the API's `phrases` array; legacy semicolon text is split), and `FrequencyRangePicker` sets an optional range with two MHz steppers and a two-handle band bar (keyboard and screen-reader adjustable) that emits integer Hz. New rules stay enabled, high priority and scoped to the selected radio; removing a rule asks first. Pure logic lives in `incident-model.ts` (tested in `incident-model.test.ts`).

`IncidentClient` uses the supplied instance URL and bearer session through the shared SDK. It validates incident records and returned instance identity. Screen context changes abort in-flight requests and discard stale results, keeping previous-server records out of a newly selected instance. Controls reflect radio permissions; the API remains authoritative.

Callsign candidates do not authenticate speakers, spoken places do not establish positions, and interpretations do not grant radio control. Resolution and dismissal require a decision note. New incidents hold source evidence until an operator explicitly releases it.

The feature supports Expo web and React Native components without platform-specific imports. Typechecking has passed; integrated browser interaction and native development-build acceptance remain separate gates. Integration owns application navigation and mounting this screen.
