# Operational core composition

The backend now composes persisted local authentication, explicit radio permissions, installed driver factories, the radio runtime, supervised media, capture, history and jobs. It runs one runtime process per station. Multiple backend replicas must not control the same physical device.

Set `DATABASE_URL` to enable station operation. Without it, only discovery and health are available and discovery accurately advertises authentication/control as unavailable. Migrations are versioned, checksum checked and applied under a database lock. `SIGNALDOCK_DATA_DIR` persists identity, private station secrets and recordings; it must be included with database backups. The first-start `station-secrets.json` contains the one-time setup token and provider encryption keyring. It is created atomically with mode `0600`; it is never returned by an HTTP endpoint or printed at startup. Copy its setup token into the administrator setup screen locally. No default administrator password exists.

For local development, start the portable database using `node packages/database/scripts/dev-postgres.mjs`, then set `DATABASE_URL` to its printed local connection information and run `npm run dev:api`. Start the client separately with `npm run dev:client`. Select `http://localhost:3000` in the client, complete setup, and sign in. Only loopback development permits HTTP. Configure `SIGNALDOCK_ALLOWED_ORIGINS` for the actual web origin. A same-origin deployment can set `SIGNALDOCK_COOKIE_ORIGIN`; other instances use isolated in-memory web credentials or native secure storage.

Administrators configure radios and assign their own and other users' explicit radio grants. Administrative status alone grants no listening, control or transmission. The two simulator connectors are available for explicitly configured fixtures; none is silently created. They do not claim audio or PTT support. The radio dashboard and media controls share a mounted workspace so acquiring control remains effective while using its audio controls. Changing radio/server/account or navigating away stops active media before the new context is shown.

For VGC, launch the private Python service as described in [the module guide](vgc.md), register `vgc-benlink` with its Unix endpoint and an opaque `credentialRef`, and supply `SIGNALDOCK_DRIVER_CREDENTIALS_FILE`. This private JSON file maps credential names to absolute token-file paths. Public configuration cannot inject token values or execute a driver process. Startup establishes a new controller epoch only after confirmed idle. Experimental physical TX remains disabled until its explicit hardware gate passes.

Configure `LIVEKIT_URL`, `LIVEKIT_API_KEY` and `LIVEKIT_API_SECRET` to enable live media. Audio-capable installed gRPC drivers attach independently of browser listeners so receive capture does not depend on an open client. Exact generation/revision snapshots determine recording context. Missing or contradictory historical tuning remains unknown. Coverage starts from actual RX audio ingress, ends at the last frame after interruption, and is conservatively marked with an unknown end after process restart. TX capture uses the supervised microphone/TTS path after driver-stream acceptance. No transmission is restored on restart.

The integrated PostgreSQL acceptance suite verifies colliding usernames across instances, prefix deployment, explicit grants, two independent radios, lease conflicts, stale tuning rejection, recorded WAV context/range playback, logout invalidation, and persistent instance/recording recovery. The complete core check currently passes 167 tests, including real Python gRPC and synthetic production VGC interoperability. These results do not substitute for browser microphone/RF acceptance, native-device execution, or physical Linux/Raspberry Pi validation.
